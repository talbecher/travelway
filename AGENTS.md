- My Maps import writes source + recs + links via the `import_my_map` RPC (one transaction) with no Places calls inside import; optional post-success identity review is scoped to new IDs and isolated from full-trip scanning. Why: pin import must succeed independently of enrichment.
- Read-only AI API (`/api/public/trip-context`) authorizes every request via the server-only `api_resolve_token` RPC (hash, scope, live owner/shared check) and then reads with the admin client filtered by the resolved trip id; `api_tokens` has no client grants. Why: PATs are not Supabase sessions, so RLS cannot see them and the guard must live in one place.
- Name lookups on `recommendations` filter by the generated `name_norm` column (= lower(btrim(name))), not the expression. Why: RLS runs as a security barrier, so only leakproof index quals skip per-row `can_access_trip`; an expression filter caused My Maps import timeouts.
- Single-day AI "replace" runs only through the `replace_day_entries` RPC (SECURITY INVOKER; one transaction: lock, fingerprint check, snapshot, targeted delete, insert, server-side time sort), with `_day_replace_rows` as the single source for the protection rule and fingerprint, and `day_replace_runs` (insert pending only, trigger-guarded one-way transition) for idempotent retries. Why: a failure must leave the day intact, and retries must never replace twice.
- `day_replace_runs` writes require the transaction-local flag `app.in_replace_day_entries`, set only inside `replace_day_entries` after auth/input checks and restored before each return; the guard trigger (INSERT+UPDATE) also checks trip/day match, and clients have no DELETE. Why: SECURITY INVOKER needs table grants, so the trigger is what stops forging runs over REST.
- Chat-submitted day replacements are stored in `day_replace_proposals` (created only by the service-role `api_create_day_proposal` for tokens with the `propose_day` scope, which is limited to one trip) and applied only by `apply_day_proposal`. That function locks the proposal row through `_proposal_claim`, which checks access, expiry, the token and the fingerprint the user saw, then runs `replace_day_entries` with the stored content and the proposal's `request_id`. "Applied" is derived from a `done` run. Why: PATs never write directly, and retries reuse the existing idempotency instead of a second log.
- Chat checklist changes are stored in `checklist_proposals` (created only by service-role `api_create_checklist_proposal` for one-trip tokens with `propose_checklist`; content immutable via guard trigger + `app.in_checklist_proposal` flag) and applied only by SECURITY DEFINER `apply_checklist_proposal`, which locks the proposal, re-checks live access/token/expiry, compares per-task signatures (conflict), blocks unaccepted duplicates, and touches only targeted ids; the proposal's `status` is the idempotency guard. Why: DEFINER avoids needing client write grants on the proposal table, and PATs never write tasks.
- Token scopes: `read` = full trip read (all legacy tokens); `read_checklist` = checklist section only; propose scopes are independent and never imply read. Why: new permissions must not silently widen existing tokens.
- Checklist display sorts stay in the browser-only sort helpers; task details reuse BottomSheet without mutation controls. Why: presentation changes must not alter stored task order or completion.
- Pre-trip light-home layout overrides live under `html:not(.dark) .pretrip-home` in the global stylesheet; retain the existing component tree. Why: dark mode and other home states must keep their original layout and behavior.
- DayMap must be dynamically imported and rendered behind ClientOnly with Suspense. Why: its Leaflet imports access window and crash server route evaluation.
- Day-detail, recommendation add/save and Nearby consumers share the pure day-location resolver; linked recommendation/hotel locations attach only to read-time entries. Why: pins, saved selections and distances must agree without null coercion or viewport coordinates.
- Recommendation identity uses authenticated bounded matching and signed review receipts with full-row compare-and-set for existing rows; media is explicit on-demand component state, never persisted. Why: prevent ambiguous matches, stale overwrite, cross-trip writes and durable Google media caching.
- Identity bulk review uses capped automatic five-row requests and five-receipt apply batches; reload persistence is user/trip scoped and contains only own row IDs, cursor, statuses and counters, with fresh review required after reload. Why: large trips remain practical without persisting transient Google metadata or stale approvals.
- Day route ordering lives in the pure module src/lib/day-route-order.ts; entries without coordinates or with a set time are fixed at their original slots and only free-floating located stops reorder. Why: the optimizer must never push notes/timed items to the end of the day, and the pure module is unit-testable without route imports.
- Chat day-proposal locations are resolved once in `api_create_day_proposal` and stored inside immutable `entries` with parallel `location_sources`; apply passes content unchanged. Why: what the user reviews must be exactly what is applied, with no guessing at apply time.
- Bottom navigation's additional destinations reuse the shared BottomSheet and close on navigation; map-pick cards read the live recommendation query by ID. Why: preserve drawer behavior and reflect identity updates without reopening the card.
- `api_create_expense_proposal` has exactly one signature with 6 parameters: `(_hash, _trip_id, _request_id, _ops, _note, _live_fx jsonb DEFAULT NULL)`, owner `postgres`, SECURITY DEFINER, EXECUTE only for `service_role`. Never recreate the old 5-parameter version (`CREATE OR REPLACE` with 5 args adds a second overload and breaks API calls); its current definition is `drizzle/migrations/0015_expense_proposal_live_rate.sql`; change it only by `CREATE OR REPLACE` of the 6-parameter signature and re-run `drizzle/pending/0015_expense_proposal_live_rate.postcheck.sql`. `_live_fx` comes only from server code (`src/lib/fx.server.ts`), never from the API caller, and the live rate is stored per operation in `money`, never in `base`. Why: API expense proposals fall back to the live market rate without trusting a client-supplied rate, and review/apply conflict checks must stay unaffected.
